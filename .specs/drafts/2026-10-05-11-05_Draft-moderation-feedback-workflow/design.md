## 文件定位與設計摘要

對應 [requirements.md](requirements.md) 的 R1～R8，以既有 detection、command 模組增量設計，不重寫規則引擎或已完成的窗口。以下新增型別、設定與指令都是提案，並非目前程式 API。

## 已知契約狀態

| 契約 | 已核對現況 | 設計限制 |
|------|------------|----------|
| `BehaviorStore.Observe` | 回傳 `[]string`，Redis 交易產生重複計數，未回傳刪除快照 | 自動清理需新快照契約，不能從一個訊號推測目標 ID |
| 重複範圍 | 原文 HMAC，同群同人；30m／3，排除首次觀測 `<= now-window` | 不改指紋、短窗口與原子去重語意 |
| `/purge` | `FindDuplicateMessageIDs` 由 PostgreSQL 稽核目標查指紋，範圍 48h、上限 100 | 其 `created_at` 與 Redis 首次觀測時刻不是同一契約，不直接拿它替代重複快照 |
| 自動處置 | `EnforcementAction` 目前僅 Key／Kind，執行時使用當前訊息 ID | 必須能保存每個歷史刪除目標，不能所有動作都刪當前訊息 |
| 人工樣本 | 唯一鍵為 chat＋message；重複新增採 DoNothing | `/ham` 需要明確修正 API，不能再呼叫新增並宣稱已改標籤 |
| 向量 | 支援 spam／ham；現有向量唯一鍵與查詢沒有 chat 維度 | 群內人工回饋不能直接覆寫全域共享向量，需設計來源與範圍 |
| 預覽 | 沒有只讀預覽服務；正式 Processor 會占用 update、觀測計數與處置 | 不能直接呼叫正式 Process 再用 observe 模式冒充只讀 |
| schema | 現有 Store 使用 GORM AutoMigrate；未確認版本化 runner | schema 變更前需確認 migration 與部署契約，不自行擴大成全專案遷移 |

需求來源是本次三項建議與已完成窗口規格。未讀取正式設定，不知道線上 app／AI 模式、權限、部署版本與資料量；不能假造已啟用功能、測試結果或歷史原文。

## Bounded Context

包含：detection 的重複政策、處置計畫、人工樣本有效版本與預覽；command 的管理員入口；必要的 config、Redis／Memory、PostgreSQL、Telegram adapter、組裝與測試。

不包含：autoreply 業務、AI provider／prompt 重做、中文規則重寫、公開 Web UI、語意聚類、自動白名單、全群歷史掃描、外部專案程式移植與線上部署。

## 設計原則

- 偵測證據與處置政策分離：維持 `repeated_content` 不替規則加分；新增獨立政策來源，不偽造 critical 規則命中。
- 先持久化明確計畫，再呼叫 Telegram；每個目標與動作可追蹤、可接續。
- 同群同人同指紋的候選範圍不可由重試擴大；未知不當作安全成功。
- 人工標記是樣本回饋，不是模型微調，也不是永久豁免。
- 預覽共用純判定元件，不共用正式副作用流程；必要指令稽核與限流另行處理。

## 第一階段：重複處置與回溯清理

### 設定提案

```yaml
behavior:
  repeat_window: 30m
  repeat_threshold: 3
  repeat_action: observe # 新提案：observe、delete、ban
```

提案 ENV 為 `BEHAVIOR_REPEAT_ACTION`，沿用 ENV > YAML > 預設值；未知值啟動失敗。假設預設 `observe` 以保留舊行為，尚未更新 sample 或正式設定。單次清理上限採 100 則，含當前訊息；先不另開無界清理選項。

### 模式上限

此表只描述重複政策產生的動作，其他規則或 AI 來源仍依自身契約運作。

| 全域 app 模式 | repeat=observe | repeat=delete | repeat=ban |
|---------------|----------------|---------------|------------|
| `observe` | 記錄 | 記錄 | 記錄 |
| `delete-only` | 記錄 | 清理重複訊息 | 清理重複訊息，不封鎖 |
| `enforce` | 記錄 | 清理重複訊息 | 清理重複訊息並封鎖 |

AI 模式只限制 AI 來源的動作，不能放大全域權限；新的明確重複政策不以 AI 是否啟用為前提。升格前須將各來源合併規則固定為測試矩陣，避免沿用單一 `effectiveMode` 誤降或誤升其他來源。

### 目標流程與資料提案

1. 沿用 allowed chat、update 去重及成員豁免檢查。
2. 行為 port 提案回傳結構化 observation：既有 Signals，加上 Repeat 的 count、觀測時刻、窗口與最多 100 個唯一訊息 ID；沒有完整候選時明示截斷。
3. Redis 在同一原子交易內完成清除過期、NX 插入、計數與有界候選讀取；Memory 提供對等快照。當前 ID 一定納入，不能讓窗口外、其他人或其他指紋混入。
4. 以獨立 repeat policy 產生處置意圖，與規則／AI 動作合併。同一事件最多計一次違規，不為刪除前兩則各加一次；假設單純 repeat delete 不推進一般違規階梯，repeat ban 留獨立原因供稽核，升格時確認。
5. 持久化觸發原因、政策版本、候選快照及逐項計畫；每項包含 chat、user、目標 message ID 或 ban 目標、動作、狀態及錯誤摘要。去重鍵須覆蓋跨事件重複刪同一訊息，不只使用觸發事件 ID。
6. 執行前再次確認管理員／信任名單保護；封鎖沿用現有 ban 語意。逐項刪除可使用既有 DeleteMessage；採批次 API 時也不能把整批成功等同於每則確實被刪。
7. 已確認成功項目不重做；可重試失敗沿既有重送路徑接續。當前與舊訊息刪除分別記錄，不因一項失敗就宣告整批完成；持久化既有計畫不重新擴大窗口。

候選快照來自已觀測狀態，不依賴第三則已寫入 PostgreSQL 才能找到自己。Bot 重啟、紀錄過期或容量降級導致缺失時不推算不存在的 ID；若在快照保存前失敗，回復策略必須區分可重新觀測與已持久化計畫。外部成功但本地記錄失敗仍有結果不確定區間，禁止宣稱嚴格 exactly-once。

既有 `/purge` 48h 人工契約不變。刪除限制、權限與限流按實作時 Telegram 官方契約核對；本文件的 100 則是專案清理上限，不宣稱所有目標都一定可刪。

## 第二階段：人工垃圾與正常樣本回饋

### 指令提案

- 回覆訊息使用 `/spam [category] [delete|ban]`：提交垃圾標記，依明示或預設動作處置目標。假設省略動作時只刪文，不能猜測未知參數或靜默升級封鎖。
- 回覆訊息使用 `/ham [原因]`：新增或修正正常標記，不自動解封、清警告或加入信任名單。
- 已刪除訊息：規劃以稽核 event ID 選定本群目標的入口，具體語法須在 T0 確認；沒有原文與可重用向量時只能修正 metadata，回報需重新提供文字，不能從指紋回推原文。
- `/feedspam` 保留相容且不自動處置；必要時共用新版樣本服務，但不能改變既有指令副作用。

每次寫入與處置皆重新確認操作者管理員身分、目標範圍與保護狀態；不依賴過期管理員快取執行人工封鎖。人工管理命令與自動 app 模式分開說明，沿用既有人工指令授權語意，不擅自把自動 observe 解讀為人工命令被停用。

### 樣本修正與一致性

- 新增可稽核 revision／來源／有效標記，支援同一 chat＋message 修正；保留操作者、先前標籤、原因、時間及 command 去重鍵。
- 標籤更新採資料庫交易與版本檢查，避免並行舊請求覆蓋較新修正；舊向量工作完成時必須再核對 revision，不能把新 ham 改回 spam。
- 新人工回饋以群組範圍生效。現有無 chat 的共享向量不得被局部修正直接覆寫；需另建可帶來源／scope 的人工向量契約或先完成經確認的 schema 擴充。
- 有效人工樣本查詢只使用最新有效版本；同指紋多筆人工標記衝突時明示衝突，不用資料庫寫入順序任意決定。修正後的 AI 快取需以群組與回饋版本區隔或精確失效，不能命中舊標籤相關結果。
- 正常樣本仍是語意／AI 輔助證據，不直接繞過明確規則或明示的重複 ban 政策；預覽須揭露此限制，帳號解封仍走獨立已授權操作。
- 樣本保存先於可選處置；向量服務停用或失敗不抹除已確認的人工標記，分別回報「已保存／未向量化／處置結果」。無原文常態保存時，不能承諾背景重試向量化無需新輸入。

需補 migration、舊資料相容及回滾計畫；尚未選定具體表名、欄位或 runner，這些不是可直接套用的資料庫變更。

## 第三階段：判定預覽與中文回歸

假設入口為管理員回覆 `/check`，明示選項才呼叫 AI；精確語法於 T0 確認。預設讀取目前規則及歷史稽核，不觸發付費模型，也不假裝已完成 AI 檢查。

診斷服務以只讀 port 組裝，輸出：

- 規則版本、分類、分數、門檻與命中項目。
- 重複窗口／門檻、已知唯一訊息數與是否已含目標訊息；未觀測時顯示假設加入後的預估，不能多算一次。
- AI／語意是否啟用、實際執行／快取／跳過／失敗與原因、可得的標籤及信心。
- 各來源政策、全域模式、預計動作、清理候選數、豁免或缺資料原因。
- 清楚區分「當時已記錄結果」與「目前版本重新預覽」，不把目前設定說成過去部署狀態。

不得呼叫正式 Processor、Observe 或正式 AI 稽核／快取寫入服務；共用純 Detector、政策決策及只讀查詢。可記錄查詢命令稽核、限流與回覆，但不新增正式 detection／violation／sample，也不呼叫處置。不得回覆秘密值、完整 prompt 或他群資料；長輸出採摘要且逸出 Telegram 格式字元。

中文資料集納入使用者原例：`带码来干 收米一天1W`、`国庆风口来收米 赚1W`、`帮我洗洗米 赚九千`、`有码的来帮我洗米稳定秒结日挣1W`、`有码来洗米 日挣1W`、`能帮我洗米的来 日挣1w`；補正常反例 `幫我洗米煮飯`、正常收款討論、新聞引用與重複 `收到`。分開驗證單則規則、語意／AI mock、時間序列與最終政策，不把樣本內通過率當成線上命中率。

## 風險與處理方式

| 風險 | 處理 | 驗證 |
|------|------|------|
| 正常重複被封鎖 | 保守預設、模式上限、明示政策來源 | R1、R3、R8 |
| 回溯清理越界 | 原子快照、精確 ID、100 則上限、不可變計畫 | R2、R4 |
| 錯誤被當全部成功 | 單項結果、可重試與未知狀態分離 | R4、R5 |
| 樣本投毒或跨群改標 | 即時管理員授權、scope、revision 與衝突檢查 | R5、R6 |
| 預覽污染計數或付費 | 只讀依賴、外部 AI 明示啟用、限流 | R7 |
| 無 schema 發布契約 | T0 確認版本化 migration 與回滾邊界 | T0、V1 |
